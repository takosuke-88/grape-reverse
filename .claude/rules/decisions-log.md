# Decisions Log (意思決定・変更履歴)

## 2026-09-13: ぶどう未計測時に設定判別が設定1へ張り付く不具合を修正

- **症状**: ファンキージャグラー2で総ゲーム数2500・BIG14・REG15（合算1/86.2。設定6の1/119.6を大きく上回る）を入力しても、縦棒グラフが**設定1=72.1%で最有力**のまま動かない。ボーナスをどれだけ加算しても高設定側へ寄らない。ユーザーからの実使用報告で発覚。
- **根本原因**: `calculateMultinomialEstimation`（ジャグラー用の多項分布モデル）が、**ぶどうを1回も数えていない（`k === 0`）場合でもぶどうを観測対象に残していた**。ハズレ確率は `pOther = 1 - pBig - pReg - pGrape - pCherry` で求めるため、ぶどう未計測だと残りの2471ゲームが「ぶどうが1回も出ていない2471ゲーム」という偽の観測になる。これはぶどう確率が最も低い設定（＝設定1、1/5.94）に最も適合するため、ボーナス14+15回分の証拠が2471回分の偽の証拠に完全に押し潰されていた。
- **修正**: `const pGrape = ignoreGrape || !denomGrape || k === 0 ? 0 : 1 / denomGrape;` と `k === 0` を条件に追加し、未計測時はぶどうを観測空間から外す（ハズレ確率から差し引かない）。**チェリーは元から `c > 0 &&` という同じガードを持っており、ぶどうだけこのガードが無かった**のが原因。その形へ揃えただけの1条件の追加。
- **実測での確認（ファンキージャグラー2 / 2500G / BIG14 / REG15 / ぶどう未計測）**:

| | 設定1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|
| 修正前 | **72.1%** | 26.0% | 1.8% | 0.1% | 0.0% | 0.0% |
| 修正後 | 0.6% | 1.4% | 3.6% | 10.8% | 21.1% | **62.5%** |

- **既存挙動への影響はゼロ**: 追加した条件は `k === 0` のときだけ発火するため、ぶどうを数えているユーザー（`k > 0`）の計算式は1文字も変わらない。実機でも同条件にぶどう440回（1/5.68）を足すと設定6=66.6%となり、ぶどうデータがより高精度に効く従来の挙動が保たれていることを確認済み。
- **ハナハナは影響なし**: ハナハナが使う `calculateEstimation` は別関数で、`if (count === 0) return;` により未計測要素を元からスキップしている。本不具合は多項分布モデル（ジャグラー）固有。
- **2026-09-11エントリとの関係**: 前任者ページ向けに追加した `ignoreGrape` オプションは、まさにこの病理（ぶどう未計測を観測対象に残すと低設定へ張り付く）への対処だった。しかし**同じ病理が小役カウンターページ本体にも存在していることを当時見落としていた**。「ぶどうを数えない使い方」を想定から外していたのが原因。今後、特定の入力が未計測（0）の場合にモデルがどう振る舞うかは、オプションの追加時だけでなく**本体の呼び出し経路でも必ず確認すること**。

## 2026-09-13: 単独REG・チェリーREGの内訳を設定判別に反映

- **決定事項**: `calculateMultinomialEstimation`（ジャグラー）で、REGの契機内訳（単独REG / チェリーREG / 契機不明REG）を数えている場合、REG合計を内訳へ分解して尤度計算に使うようにした。ジャグラーで最も設定差が大きいのは単独REG（マイジャグラーV 設定1→6 で確率2.00倍。REG合計は1.68倍、BIG合計は1.21倍）で、その情報を捨てていたため。
- **二重計上の回避（重要）**: 「REG合計に加えて単独REG・チェリーREGも観測へ足す」のは**禁止**。同じREG1回を2回数えることになり尤度が壊れる。REG合計を内訳へ**分解**するのが正しい。
- **公表REG合計をアンカーにする理由**: 内訳の生確率をそのまま使うのではなく、**公表REG合計 × (内訳由来の単独:チェリー比率)** で各確率を求める。ミスタージャグラーは `1/単独REG + 1/チェリーREG` が公表REGと**最大4.53%ずれている**ため、生値だとREG確率自体が公表スペックから外れる。比率のみ使えば単独REGの判別力はそのまま活き、かつ**ハズレ確率（pOther）が一切変化しない**＝純粋に情報が増えるだけになる。
- **有効化の条件**: `単独REG + チェリーREG + 契機不明REG === REG合計` かつ `単独REG + チェリーREG > 0` のときのみ分解する。REG回数を直接入力した場合（内訳が0）は不一致になるため従来どおりREG合計だけを使う。全て契機不明なら分解しても結果は数学的に同一。契機不明REGは「単独かチェリーのどちらか」としてREG合計の確率で評価し、分類できなかった分も捨てない。
- **BIGは対象外**: 設定差が1.21倍と小さいうえ、`1/単独BIG + 1/チェリーBIG` が公表BIG合計と**14〜19%ずれる**機種が多い（REGは0.03%以内で一致）。使うとBIG確率が公表スペックから外れるため、BIGは合計のまま扱う。
- **効果の実測（モンテカルロ。既知設定の台を各設定800台×6設定＝4,800台生成してモデルに当てさせた）**:

| 機種 / 条件 | 6択正答率（修正前→後） |
|---|---|
| マイジャグラーV 2500G | 28.7% → 30.0%（+1.3pt） |
| マイジャグラーV 5000G | 32.2% → 34.1%（+1.9pt） |
| マイジャグラーV 8000G | 37.0% → 40.4%（+3.4pt） |
| ファンキージャグラー2 2500G | 26.1% → 26.4%（+0.3pt） |
| ファンキージャグラー2 8000G | 34.9% → 35.5%（+0.6pt） |

  回転数が増えるほど効く（REG回数が増えて内訳の統計が効くため）。劇的ではなく着実な改善。

- **同時に判明した判別精度の実力（今後の期待値の目安）**: 6択の正答率は2500Gで約30%、8000Gでも約40%（当てずっぽうは16.7%）。一方「高設定(4-6)か低設定(1-3)か」の2択なら2500Gで約71%、8000Gで約82%。**設定を特定するツールではなく、高設定の可能性が高いかを判断するツール**として位置づけるのが実態に合う。ぶどうを数える効果は+3〜5ptで、REG内訳より大きい。

## 2026-09-22: 設定判別ページを「現在 − 前任者」で判別する方式へ変更（2026-09-10の決定を覆す）

- **決定事項**: 設定判別ページ（`MachinePageFactory`）の判別を、入力値そのままではなく **「現在の入力値 − 前任者ページの入力値」** で行う。対象は詳細判別カード（判別結果・信頼度・確率指標・期待度グラフ・AIアドバイス）に加え、**各カウンターバー右下の確率表示と最下部「確率・設定差一覧」表のハイライト**まで含む、このページの確率表示すべて。バーに表示される数字（回数そのもの）は生の入力値のまま変えない。
- **2026-09-10の決定を覆している**: 当時は「『現在−前任者』の差し引き判別も検討したが不採用」と記録したが、ユーザー判断で方針転換した。**この2026-09-22の決定が最新であり優先される。** 2026-09-10エントリの「判別には混ぜない」という記述を読んで差し引きを外さないこと（禁止なのは前任者分を*足し込む*方向のみ）。
- **理由**: 総ゲーム数は前任者分を含むのに、ぶどう・チェリー・ボーナス内訳は自分が数えた分しかない。この食い違いのままでは、ぶどう確率が実際の数倍悪く計算される（実測: 現在5000G・ぶどう350回・前任者3000G で **1/14.3** という実在しない値が出る。差し引き後は 1/5.7）。
- **BIG/REGは「契機不明」から引く（重要）**: 合計から引くのではない。前任者のボーナスは契機を目撃できないため必ず契機不明バケットに入っており（合計を直接入力すると差分が契機不明へ自動吸収される `handleValueChange`）、単独/チェリーは自分が目撃した分だけ。この引き方なら **「単独＋チェリー＋契機不明＝合計」の不変条件が保たれ**、2026-09-13で入れたREG内訳判別（`useRegSplit`）が無効化されずに済む。合計から引く案は内訳と不一致になり内訳判別が自動で無効化されるため却下した（実測でも結果が変わることを確認済み: 設定3が20.0% vs 19.8%）。
- **却下した案: 内訳の按分**。調整後合計の比率で単独/チェリーREGを縮小する案は、自分が実際に目撃した「単独REG 4回」を3.2回などに書き換えることになり実データを歪めるため不採用。単独REGは判別力の核なので触らない。
- **却下した案: マイナスを許容してそのまま計算（重要）**。「現在＜前任者」という矛盾入力に対し「あり得ない数字が出れば誰でも気づく」という想定で検討したが、**実測で否定された**。マイジャグラーVの判別関数にREG=−3を通すと、棒グラフは 設定1=43.8% / 2=32.1% / 3=14.8% / 4=5.5% / 5=3.0% / 6=0.8% と**合計100%の正常な見た目**になり、正解（設定3）と真逆の設定1を自信ありげに指す。マイナスの回数は「その確率が低い設定ほど尤もらしい」という逆向きの証拠として効くため。総ゲーム数もマイナスにすると6設定すべて16.7%の均等分布になり、**未入力状態と見分けがつかなくなる**。唯一見える異常はREG確率欄の `1/-666.7` だけ。2026-09-05（差枚マイナス）・2026-09-13（ぶどう未計測で設定1へ張り付き）と同じ「エラーにならず正常に見える数字が逆方向を指す」失敗モードのため、ガード（1行）を選んだ。
- **現行仕様（判別に渡す値の決まり方）**:
  | 状況 | 判別に使う値 |
  |---|---|
  | 前任者データなし | 現在の入力値そのまま（**従来と数式レベルで同一**） |
  | 前任者データあり | 総ゲーム数=現在−前任者、BIG/REG=契機不明から前任者分を引いた合計、ぶどう・チェリー・単独/チェリー内訳は現在のまま |
  | 現在ページが未入力（総G=0） | 前任者の生データ（総G/BIG/REG）をそのまま使う |
  | 現在＜前任者（矛盾） | 判別結果を出さない（未入力時と同じ表示） |
- **実装**: `MachinePageFactory` の `judgment` useMemo が `judgmentInputs` / `judgmentTotalGames` を作り、詳細判別・バー確率・設定差一覧表がこれを参照する。バーの確率だけ分母を差し替えるため `DynamicInput` に `probCount` propを追加した（未指定なら表示値をそのまま使うので、逆算ページ・前任者ページの挙動は完全に不変）。リセットは `removePreviousData()` 経由に変更し、前任者データを消したときstateも即座に同期するようにした。
- **意図的に対象外**: ぶどう/ベル逆算ページの設定推定は従来どおり生の入力値を使う。結果として**前任者データがある台では、設定判別ページと逆算ページで判別結果が食い違い得る**。
- **既存ユーザーへの影響**: localStorageのキー名・保存形式は無変更。前任者データを入力していないユーザーには影響ゼロ（現在−0＝現在）。影響を受けるのは前任者データを入力済みのユーザーのみ。

## 2026-09-22: 差分ラベルの追加と、それに伴うトグルの縮小

- **決定事項**: 前任者分を差し引いて判別している間、総ゲーム数・BIG回数・REG回数のラベルに自分の分を添える（`総ゲーム数 差分 2000G` / `BIG回数 差分 7回` / `REG回数 差分 6回`）。あわせて `CurrentPreviousToggle` / `DiffSignToggle` を **204×52px → 140×48px**（ボタン `w-24`96×44px → `w-16`64×40px）へ縮小し、`DiffSignToggle` は記号を落として「プラス／マイナス」の語のみにした。
- **理由**: 「今自分が何回ボーナスを引いたか」を知るのに、前任者ページと往復して暗算する必要があった。バーの数字はデータランプの累積値（例: 17）のままなので、自分の分（7）が画面のどこにも出ていなかった。
- **ラベルを「BIG差分」に置き換えなかった理由**: 当初の要望は `BIG差分 7` だったが、**バーに出ている数字は差分ではない**（17）。ラベルを「差分」にすると17が差分に見えるため、`BIG回数 差分 7回` の形にして「BIG回数」がバーの数字を、「差分 7回」が自分の分を指すようにした。
- **括弧を外した理由（実測）**: 当初 `BIG回数（差分 7回）` としたが、総ゲーム数は5桁になるため `総ゲーム数（差分 12000G）` が179.7pxとなり、ラベルに使える171.3pxに入らなかった。括弧は全角2文字分あり、外すと155.5pxまで下がって収まる。BIG/REGも括弧なしなら3桁（`REG回数 差分 123回` 128.4px）まで2列セル147.6pxに収まる。
- **トグル縮小の必要幅（実測・375px）**: カード内側311.3px。トグル204pxのときラベルに使える幅は**107.3px**しかなく、`総ゲーム数 差分 2000G`（147.5px）が入らない。トグルを140pxにすると**171.3px**へ広がる。
- **`DiffSignToggle` の記号を落とした理由**: 「現在」32px・「前任者」48pxは64pxボタンに収まるが、「＋プラス」67.7px・「−マイナス」**75.8px**は収まらない。語のみなら「マイナス」55.7pxで収まる。文字を小さくして記号を残す案（記号`text-base`／語`text-xs`で62.7px見込み）もあったが、可読性を下げるため不採用。逆算ページだけトグルを大きいまま残す案も、「トグルの存在感を下げたい」という要望に反するため不採用。
- **差分ラベルを出す条件**: 差し引きが成立している `mode === "diff"` のときだけ。現在ページ未入力で前任者の生データを使っている場合（`prevOnly`）と、矛盾入力で判別を止めている場合（`invalid`）は、表示される値が差分ではないため出さない。前任者データがあれば、その要素の前任者値が0でも表示する（`BIG回数 差分 17回` のように生の値と同じ数字が出るが、差分モードであることが一貫して分かる方を優先）。
- **タップ領域について**: ボタンは96×44px → 64×40pxとなり、iOS/Androidが推奨する最小44pxをわずかに下回る。`coding-style.md` §2 の「巨大なタップ領域」方針に対しては後退だが、ページ切替時にしか押さないコントロールであること、ユーザーが実機で「迷わず押せる」と確認した上での判断。**カウンターバーの＋/−には適用しないこと**（あちらは実戦中に連打する主操作）。

## 2026-09-22: リセットの範囲を「連動＝セット／独立＝単独」へ整理

- **決定事項**: リセットで消える範囲を次のとおり変更し、確認ダイアログに削除範囲を明記した。

| 逆算ページ | 残る | **残る（変更点）** | 消える |

- **理由**: 判別が「現在 − 前任者」で連動したため、設定判別と前任者は片方だけ残すと破綻する（残った入力が別基準で判定される）。逆に逆算ページは判別に関与しないので、他ページのデータを消す理由がない。従来は逆算ページのリセットでも前任者データを消していたため、**「ぶどう逆算の入力をリセットしたつもりが、設定判別ページの判別結果まで変わる」**という予期しない副作用が生じていた（差分ベースから生の値ベースへ戻るため）。
- **確認ダイアログの文言**: 「消える範囲がダイアログに書かれていない」状態も問題だった。特に逆算ページは「**ぶどう逆算の入力を**全てリセットしますか？」と範囲を限定した書き方なのに、実際には別ページのデータまで消していた。現行の文言は以下。
  - 設定判別ページ: 「このページの入力を全てリセットしますか？\n\n前任者ページに入力した内容も一緒に削除されます。」
  - 前任者ページ: 「前任者データをリセットしますか？\n\n設定判別ページに入力した内容も一緒に削除されます。」
  - 逆算ページ: 「{ぶどう|ベル}逆算の入力を全てリセットしますか？」（変更なし。実態と一致するようになった）
- **キー定義の集約**: 前任者ページが設定判別ページのキーを消す必要が出たため、`previous-data-storage.ts` に `counterDataStorageKey` / `bonusHistoryStorageKeys` を追加し、`MachinePageFactory` 側もそれを使うようにした。同じキー文字列を2箇所で書くと、将来キー名を変えたときに片方だけ追従せず「リセットしたのに消えない」という静かな不具合になるため。**キー名そのものは1文字も変えていない**（既存ユーザーのデータが読めることを実機で確認済み）。
- **実装上の細かい挙動**: 設定判別ページのリセットは `setBigHistory([])` で履歴を空配列にするためキー自体は残る（値は `[]`）。前任者ページからのリセットは `removeItem` でキーごと消す。どちらも履歴が空になる点は同じ。逆算ページも `setGrapeData({})` なのでキーは残り値が `{}` になる。

## 2026-09-22: 破壊的操作の確認を `window.confirm` から `<dialog>` ベースの自前モーダルへ

- **決定事項**: 全体リセット3箇所（設定判別・前任者・逆算）の確認を `useConfirmDialog`（`src/components/ui/ConfirmDialog.tsx`、新規）へ置き換えた。`coding-style.md` §2 の「必ず `window.confirm` による確認ダイアログを挟む」も改訂済み。
- **`window.confirm` をやめた3つの理由**:
  1. ブラウザが「**{オリジン} の内容**」という見出しを強制的に付け、JS側から消せない。LAN経由のテストでは「192.168.x.x:5000 の内容」というIPアドレスが出る（本番ではドメイン名になるが、いずれにせよユーザーには不要な情報）
  2. CSSが一切効かないため、直前に追加した警告文（別ページのデータも消える旨）がプレーンテキストに埋もれて読み飛ばされる
  3. **同じダイアログを繰り返すと「このページでこれ以上ダイアログを表示しない」が出る。チェックされると `confirm()` が無言で false を返し続け、リセットボタンが原因不明で効かなくなる**。こちらからは検知も解除もできない
- **div で自前実装せず `<dialog>` を選んだ理由**: div方式はiOS Safariの100vh問題・背面スクロール固定（iOSは`overflow:hidden`だけでは止まらない）・フォーカストラップ・Escキー・セーフエリア・**stickyヘッダー（`z-50`）とのz-index競合**を全て自前で背負う。`<dialog>` + `showModal()` はこれらをブラウザが処理し、**top layer に描画されるためz-index競合が構造的に起こらない**。CSSは完全に効くので見た目はサイトに統一できる。
- **フォールバック**: `HTMLDialogElement.prototype.showModal` が無い環境（iOS Safari 15.3以前、2022年3月より前）は `window.confirm` へ自動で落とす。警告文は改行で連結して渡す。
- **API**: `const { confirm, confirmDialog } = useConfirmDialog();` で、`const ok = await confirm({ message, highlights?, confirmLabel }); if (!ok) return;` の形。`{confirmDialog}` をページ直下に置く。**非同期化が一番危ない箇所**（キャンセルしたのに消えると最悪の事故）なので、3ページ×4挙動（キャンセル／Esc／背景タップ／実行）を実機で確認済み。
- **UI仕様**: 左＝キャンセル（グレー）、右＝実行（`bg-red-600`。`coding-style.md` §2 の「破壊的操作は赤」に従う）。背景タップとEscはキャンセル扱い。ボタンは `min-h-[48px]`。
- **文面は1行だけ**: 見出し・補足文・別枠の警告ボックスは置かず、「何が消えるか」を1文で書く（例: `設定判別ページと前任者ページの内容を全て削除します。`）。消える範囲のページ名を `highlights` に渡すと、その語だけアンバー（`amber-700`／dark時`amber-300`）の極太で強調される。赤はリセットボタン専用なので文字色には使わない。
- **`highlights` が文字列分割方式である理由**: JSXで色付きの文面を直接渡す設計にすると、`window.confirm` フォールバック用に平文をもう一つ用意することになり二重管理になる。`message` を文字列のまま保ち強調語だけ別指定することで、**フォールバック時も同じ文面がそのまま使える**（色は失われるが情報は落ちない）。
- **右下が破壊的ボタンになる点**: 片手操作で親指が最も届く位置に「リセット」が来るが、iOS標準の配置（左キャンセル／右実行）と同じであること、確認ダイアログという二段階目であることから許容した。誤タップが問題になったらボタン間余白の拡大を検討する。

## 2026-09-22: 詳細判別カードの指標に実測回数を表示

- **決定事項**: 指標カード（`ProbabilityMetricCard`）のラベル横に、その確率の母数になっている実測回数を出す（`BIG確率 7回`）。前任者分を差し引いている場合は差し引き後の回数（カード内の確率と同じ基準）。0回（未計測）のときは何も出さない。設定判別ページ・前任者ページの両方に適用。

- **幅の上限（実測・375px）**: カード内側126.0px。数字は最も幅の広い「0」で計測した最悪ケース。

- **シミュレーションでの裏付け**: マイジャグラーV設定6相当の出方で1000G〜15000Gまで当てたところ、**全ての回転数で9枚とも14pxに収まった**。桁が増え続けるのは`ブドウ`だけで（6000G以降4桁＝92.0px）、他は2桁で頭打ちになる。12pxへ落ちるのは`チェREG`3桁（約76,000G）・`フェザー`3桁（約23,000G）など実使用ではまず到達しない領域。
- **実装で踏んだ落とし穴（再発）**: 最初の実装は検出が全く効かなかった。ラベルがflexアイテムで中身の幅に張り付き、`clientWidth`と`scrollWidth`が常に一致していたため。**ラベルの箱に `w-full min-w-0` を付けて**カード幅にそろえ、14pxで測る間だけ `overflow-hidden whitespace-nowrap` にしてはみ出しを`scrollWidth`に出す。2026-08-05の`min-w-0`と同じ原因。
- **無限ループの防止**: 判定は縮む方向にしか動かさない。12pxのときに測っても「14pxなら入るか」は分からないため、**表示中の文言が変わったときだけ14pxへ戻して測り直す**。画面回転（resize）でも測り直す。
- **実機で確認した挙動**: 通常時は9枚とも14px・カード高さ89px。`チェREG`を999回にすると9枚同時に12px・85pxへ落ち、16回に戻すと9枚同時に14pxへ戻る。**リロードせずカウンターへ入力した瞬間に切り替わる**。`useLayoutEffect`で描画前に判定するためチラつきは出ない。

## 2026-09-23: 指標カードの並びを意味のまとまりで整理し、空きマスを確保

- **決定事項**: 3列化した指標グリッドの並びを、行ごとに意味がまとまるよう組み替えた。2枚しかない行は**3つ目を空きマスとして確保**し、左2列が縦に揃うようにする。

| 行 | ジャグラー（12マス） | ハナハナ（9マス） |
|---|---|---|
| 1 | BIG / REG / **合成** | BIG / REG / 合成 |
| 2 | 角チェ / ブドウ / （空き） | 角チェ / ベル / （空き） |
| 3 | 単BIG / チェBIG / （空き） | スイカ / フェザー / （空き） |
| 4 | 単REG / チェREG / （空き） | — |

- **理由**: 合成確率がBIG確率・REG確率から3行離れていて並べて見比べられなかった。1行目にボーナスの合計3つを集め、2行目に通常時小役、3・4行目にBIG内訳・REG内訳を置く。ハナハナはBIG/REG内訳が存在しないため、3行目をBIG中の要素（スイカ・フェザー）に充てる。
- **空きマスを詰めない**: 2行目以降は2枚しかないが、`null`のセルをグリッドに残す。詰めると行ごとにカードの位置がずれて左右がガタつく。
- **実装**: 並び順を `layout` 配列（ラベル名の並び、`null` が空きマス）に切り出し、`metricItems` からラベル名で引いて描画する。**カードの定義そのものは動かしていない**ので、確率の計算には一切触れていない。
- **空きマスへ指標を足す手順**（今後の追加を想定した作り）: ①`metricItems` の配列に1件足す ②`layout` の `null` をそのラベル名に差し替える。この2箇所だけでよい。
- **足すときの制約**:
  - **ラベルは全角3文字＋3桁までが安全**（`角チェ 337回` で84.0px／枠92.0px）。全角4文字だと `フェザー 000回` が98.0pxで入らず、**グリッド全体が12pxへ落ちる**（1枚でも入らなければ9枚そろって落とす仕様のため、長いラベルを1つ足すと全部小さくなる）。
  - 値は `1/◯◯` の形が決め打ち（`ProbabilityMetricCard` の `1/${format(val)}`）。機械割や差枚のような**確率以外を出したい場合はカード側に `1/` を付けない選択肢を足す必要がある**。
